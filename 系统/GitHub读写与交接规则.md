# GitHub读写与交接规则

## 固定入口与一次性设置
仓库为 https://github.com/qq1464356758-del/xiaoshuo3 ，main 分支，根目录，XIAOSHUO3。
用户只需在七个普通聊天对话分别加载角色指令，并使这些对话能实际调用GitHub读写。新对话的工具可用性要在第一次正式任务验证，不由其他对话的成功代替。
初始化完成不代表已有小说设定。总监收到灵感后才建立世界、人物与章节任务；不得把占位文件说成正式设定。

## 真实文件操作
1. 定位仓库并取得main当前提交；读取数据库入口.json、运行状态.json。正文资料按任务指定提交读。
2. 工具若支持 fetch_file，就传仓库全名、真实path和已知ref；同等能力名称不同也可。若需原始内容接口，路径为 /repos/qq1464356758-del/xiaoshuo3/contents/文件路径?ref=真实提交。
3. 搜索只用于定位，最终必须读取完整所需内容。长文件分页记录首末行，逐段覆盖，不能只读开头结尾。
4. 新文件用创建文本文件能力，传入完整UTF-8内容。更新文件先读取当前文件SHA，以该SHA更新；SHA过期就重读比较，不盲目覆盖。
5. 同一次相关写入按顺序进行。能创建树和提交时，可基于最新树将相关文件一并提交，以非强制方式推进分支；不能强推，也不能删掉未涉及的树项。
6. 写入后取得真实commit SHA，再按这个提交读回全文或原始字节，确认内容、路径、字数。Git提交SHA、文件blob SHA、文件SHA256是三种不同的值，必须明确名称；优先使用GitHub返回的文件SHA与固定提交，避免让聊天反复计算整仓哈希。
7. 消息只报告已完成的事实，不输出伪造接口回执。

## 最少调用原则
1. 仓库、main、数据库入口和系统文件路径已经固定时，不要每轮重新搜索仓库、全量列目录或做无意义“连接测试”。直接读取本轮所需固定路径和固定提交。
2. 能用一次树提交保存同一产物的正文、说明、读取记录时优先一次提交；工具只支持逐文件写入时才顺序写。不要为了同一份内容同时制造ZIP、聊天长文、GitHub副本三套传递物。
3. 下游只读取任务清单、本角色所需正文／报告和必要证据。不要因为“保险”而每章遍历整个仓库；涉及早期事实时再按索引回查对应原文。
4. 用户日常只复制末尾交接块。交接块必须已填任务、入口和真实提交，不让用户再去GitHub找路径、复制正文、下载上传文件或计算哈希。
5. 重复收到同一入口时先核验已有交付并返回同一下一步，不重复生成、重复上传、重复审核。

## 写入安全边界
1. 总监维护正式层：设定/、索引/、任务/、定稿/、运行状态.json、数据库入口.json、当前进度.md和系统规则。
2. 灵感员、写手、裁判、审核员只写任务明确授权的本角色目录。不得修改他人产物、正式设定、运行状态或定稿。
3. 已经标记“可交接”的正文或报告一律视为不可变快照。后续修订创建新版本、新路径或明确的取代报告，不覆盖旧文件。
4. 非总监角色禁止删除正式文件、强制移动分支指针或用“清理旧版本”为理由删历史。未完成草稿只有原角色可在任务指定路径续写。
5. 这些是流程权限，不是GitHub账号级ACL。共用同一授权账号时仍具有技术上的越权可能，因此每次交付必须用固定提交和不可变版本保证可追溯；不得声称实现了真正的技术隔离。

## 三种固定的版本引用
资料提交：总监先保存本轮设定与记忆，取得实际提交；任务引用这个已存在的提交。
任务提交：总监再保存不可变任务文件，取得实际提交；运行状态引用这个任务提交。
产物提交：执行者保存完整稿件或报告并读回，取得实际提交；交付.json引用这个产物提交；聊天交接引用交付.json实际所在提交。
没有任何文件需要包含自己的未来提交号。分支头变化本身不是资料作废信号；运行状态中任务身份才是。
不能按提交读时，只有逐个文件当前SHA与已记录SHA完全一致才能等价继续，注明实际读取方法；新增未绑定来源先交总监补齐。

## 不可变产物与就绪标记
任务为每个执行角色指定正文、说明、交付入口、报告等实际路径。每个版本各自独立，不覆盖先前可交接版本。
完整顺序是：生成 → 中文自修 → 工具计数 → 写正文和说明 → 读回 → 写交付.json → 读回交付.json → 输出交接。
交付.json只在正文完整、计数合格、引用核验通过时标为“可交接”。上传半章、缺说明或计数未知均不得标可交接。
写完交付.json后再检查运行状态；任务已换就只报告孤立旧产物，不向下游派发。旧产物保留供追溯，不自动覆盖。
写入超时不等于失败。先读目标路径：与预期相同则接续核验；不同则停止并交总监判断；不存在才重试同一目标。最多一次有依据的重试，不反复新建重复文件。
版本与任务的关系：一份有效任务规定每位写手唯一一份可交接正文版本；正文交付后若有改动，由总监撤销旧任务并发布新任务，继承累计返修次数。
“完整、字数合格才能可交接”专指正式小说稿件。灵感、裁判和审核报告按各自交付要求判完整；“全部退回”“材料不足”报告本身可以完整交给总监，但绝不表示正文合格。无法取得正文时如实保留未知字段，不捏造版本或计数。
裁判与审核员更正报告时，可以在任务指定的本角色报告目录中追加第02次等新报告和交付入口，必须记录“取代报告”的固定路径与提交、纠正原因、同一正文绑定；不得覆盖旧报告。总监和下游只接受明确取代链的最新有效结论；多个冲突结论无取代关系时暂停并向报告作者核验。
报告目录及追加命名规则由任务写明，报告更正不自动赋予新正文写入权。单纯更正报告不增加正文返修次数；正文重写才计入，三稿全退重写同样计入。

分支：main
任务：本轮真实任务编号
入口：本轮真实交付.json路径
入口提交：GitHub实际返回的完整提交号
请按你的角色指令执行：先核对main的运行状态，再读取上述固定提交的入口及所引全文，保存结果并给出唯一下一步。
接收者是写手B或C时，入口使用同一任务文件与任务提交，不传前一写手稿件正文，避免模仿。
裁判根据当前任务预定的三份交付入口，首次读取时取得并固定各自最新已完成版本；之后不因目录里新增文件擅自换稿。
只有首次设置和真正故障可能需要额外操作，日常不传ZIP。

## 分工与并发
默认首章按A、B、C串行转交，降低手动操作和同时写入冲突。三人各写独立全文，不读取对手正文。
用户若主动并行三稿，也可按同一任务、不同目录保存；不得同时让两个同角色对话执行同一任务。发生冲突先保留两份结果并由总监确定有效版本。
运行状态.json只有总监写，不让所有角色抢改共享“最新进度”。普通稿件上传不要求总监增加一次转交。

## 错误对应处理
没有工具／Unknown tool：报告具体未加载能力，只做一次工具发现；不反复调用不存在的名称。保留当前成果，末尾给同角色恢复指令。
403或权限不足：保留原稿，说明目标路径和读写失败；等待用户在平台完成必要授权，不暗示重写提示词即可解决。
404：核对仓库、ref、路径及权限；缺任务交总监，不把404自动当空仓库。
409或文件SHA冲突：重读当前内容与SHA，仅对自己未完成文件续写；已可交接版本不能覆盖。
半章或截断：标未完成并续写，禁止送审。
资料不足：写明实际已读和缺失，交总监补充，不能判通过。
额度耗尽：不保证继续运行；额度恢复后在原角色按断点继续，或在用户选择的新同角色聊天读数据库恢复。
用户更换仓库：先核对新入口，旧成果不自动迁移成新项目既定事实；只有收到具体迁移要求才移入并核验。
