# xiaoshuo3 聊天直连工作流审计与优化记录

日期：2026-09-11
仓库：qq1464356758-del/xiaoshuo3
目标：全部角色使用普通 Chat；GitHub 作为唯一正式中转；用户日常只复制末尾交接块；100章、每章8000—10000字。

## 审计结论
当前系统可进入试运行。未发现需要推翻架构的致命问题。
旧版“只有总监写GitHub + ZIP逐角色搬运”已经废弃。现行架构允许灵感员、写手、裁判、审核员把自己的产物直接写入各自目录，下游按固定提交和交付入口读取；总监独占正式设定、任务、运行状态、定稿和索引的维护职责。

## 本次确认已满足
1. 七个角色均以普通 Chat 对话运行，不依赖 Work 模式。
2. 日常不传 ZIP、不下载上一角色文件再上传下一角色。
3. 写手正文直接保存到 GitHub，裁判和审核员从固定提交读取。
4. 每个角色末尾必须给唯一“下一步复制给XX AI”的已填好交接块，不让用户填写路径、SHA或版本。
5. 首章三稿保持互不阅读对手正文；裁判固定读取三份交付后比较。
6. 综合审核员执行26项完整审核；每版全文检查，返修还检查联动问题。
7. 中文自然化包含去翻译腔、模板句、同质对白、万能微表情、机械总结、重复注水等具体检查；不靠一句“有AI味”退稿。
8. 定稿绑定同一正文文件SHA、审核报告和锁定凭证，避免旧报告批准新稿。
9. 运行状态只有总监写，其他角色不抢写共享进度。
10. 任务、资料、产物都使用固定提交引用，main后续新增文件不会自动使旧任务漂移。

## 本次实际优化
### 1. 裁判与审核职责拆开
旧规则让裁判和综合审核员使用同一最终通过门槛，可能导致三稿都有可修问题时三篇一起重写，浪费大量生成额度。
现改为：裁判只做候选资格检查和横向选优。只要至少一稿完整、字数合格、同一任务且无致命核心问题，就选择最佳稿进入综合审核；可修的重要问题由综合审核员集中审出，后续只返修获选稿。
最终定稿标准没有降低，仍由综合审核26项、返修闭环和总监锁定保证。

### 2. GitHub 最少调用原则
固定仓库后禁止每轮重新搜索仓库、全量列目录或做无意义连接测试。能一次提交同一产物的正文、说明和读取记录就优先一次提交；只读取本轮必要证据，早期事实按索引回查。

### 3. 非总监写入安全边界
灵感员、写手、裁判、审核员只能写任务授权的本角色目录。已经“可交接”的产物视为不可变快照，修订创建新版本；非总监不删正式文件、不强推分支、不修改他人产物、正式设定、运行状态或定稿。

## 最省心的实际流程
首次只做一次：建立7个普通 Chat 对话，把 `系统/开场指令.txt` 对应短指令分别发给灵感员、总监、写手A、写手B、写手C、裁判员、审核员。

首章：
灵感员 → 总监 → 写手A → 写手B → 写手C → 裁判员 → 综合审核员 → 总监。

第2—100章：
总监 → 已选主写手 → 综合审核员 → 总监。

返修：
总监 → 主写手 → 综合审核员 → 总监。

每一步上一个AI先把完整产物写入GitHub并读回核验，聊天只给短状态和一个下一步交接块。用户不下载正文、不上传ZIP、不找文件、不算字数、不填SHA。

## 用户日常只做一件事
看回答最底部的：
`下一步：将下面这段复制给【XX AI】`
然后整块复制到那个角色对话即可。

除以下情况外，不需要用户做决定：用户自己的核心方向冲突、需要更换主写手、连续返修达到暂停阈值、GitHub/代码工具真实不可用。

## 仍然存在但不建议为“完美”增加复杂度的风险
1. **同一GitHub账号没有真正的目录级技术权限隔离。** 当前是角色规则隔离 + 不可变提交追溯。如果改成每角色独立分支/账号/PR可以更强隔离，但会增加大量操作，不符合“快捷、方便、不用思考”的目标。
2. **普通 Chat 仍可能遇到模型或工具额度限制。** 本系统能减少无效回合和重复生成，不能承诺消除平台额度限制。
3. **跨聊天不能在本工作流内自动替用户点击发送。** 当前最少人工操作是复制一个已填好的交接块。若未来接入专门调度器，可再自动化，但不是本版必需。
4. **精确字数需要可用的代码/数据分析能力。** 没有准确计数能力时不得假装达标；保存草稿并由具备计数能力的角色核验。

## 最终原则
宁可保留少量真实、可解释的人工转交，也不要为了“全自动”引入更多状态、插件和分支，最后让系统本身比写小说更复杂。
质量门槛放在“获选稿的综合审核和返修闭环”，而不是让三个候选写手反复同时重写。
GitHub是唯一正式中转和证据库；聊天只是角色执行界面与下一步按钮。
